# Security & Trust Model

**Bottom line:** the app never stores your wallet's private key. It signs orders with a
delegated **session key** that lives only in memory. Based on RiseX's confirmed API surface it
cannot withdraw or transfer funds — but that specific guarantee has not been independently
verified beyond "no such method exists in the surface we found" (see [Known limitations](#known-limitations)).

## Two keys, two roles

| Key | Who holds it | What it can do |
|-----|--------------|----------------|
| Your wallet key | Your wallet (Rabby/MetaMask) — never exposed to the app | Signs **one** `RegisterSigner` message to register the session key. |
| Session key | Generated by the app, kept **in memory only** | Self-signs its own `VerifySigner` message, then signs every order/leverage permit. No `withdraw` method exists on the confirmed API surface. |

This is RiseX's own delegated-signer model — not the same mechanism as Hyperliquid's
`approveAgent`, though it serves the same purpose. The key structural difference: registering the
session key needs **two** signatures, not one — see [Lifecycle](#lifecycle).

## Lifecycle

1. **Connect** wallet.
2. **Approve session key** (`POST /v1/auth/register-signer`) — the app **switches (or adds, if
   not yet configured) your wallet's active network to RISE Chain first**, then generates the
   session keypair, has it **self-sign** a `VerifySigner` message (proving the new key consents
   to being registered), then asks your wallet to sign a `RegisterSigner` message authorizing it.
   The chain switch is required because MetaMask (and similar wallets) validate that a
   `signTypedData` request's `domain.chainId` matches the wallet's currently active network and
   reject the request otherwise (`"chainId should be same as current chainId"`) — found while
   testing locally against mainnet; the reference project's assumption that "the wallet's active
   network doesn't matter for signing" (true for Hyperliquid) does not hold here. Both
   signatures use RiseX's EIP-712 domain for the active network. The session is set to expire
   ~30 days out.
3. **Trade** — every order, leverage change, and close is signed locally by the session key, no
   wallet popups.
4. **Refresh / disconnect / switch wallet / expire** — the session key is discarded. A background
   check (every 30s) also actively expires a session once it passes its signed expiration, so the
   UI falls back to the approval prompt on its own rather than silently trading on borrowed time.
   You re-approve to continue.

## Where the key lives

- The session private key is a **module-scoped variable** in `lib/agent.ts`.
- It is **never** written to `localStorage`, `sessionStorage`, cookies, or IndexedDB; **never**
  logged; **never** placed in serializable React state.
- Only a key-free snapshot (approved flag + public addresses) is exposed to the UI, via
  `useSyncExternalStore`.

## The trust boundary

Authorization is enforced where signing happens, not in the UI:

```ts
getAgentAccount(masterAddress)   // throws unless an approved, non-expired session
                                 // is bound to this exact master
```

Because the current wallet address is passed at execution time and verified against the
session's bound master (and its expiry is checked live, not just at approval time), there is no
window where a stale or expired session could sign an order attributed to a different wallet.

Additional hardening carried over from the reference project's adversarial review, applied here
too:

- Re-validate after the async registration signatures; discard the result if the wallet changed
  mid-approval.
- De-duplicate concurrent approvals; short-circuit if already approved.
- The session key only ever signs order/leverage/close permits — no method to move funds out of
  the account exists anywhere in the confirmed API surface it's given access to.

## Order and action signing, in brief

Every order, leverage change, and position close is a separately signed **`VerifyWitness`**
permit (account, target router contract, an action-specific hash, a bitmap nonce, a deadline),
signed by the session key with no wallet popup. Order permits use the account's *current* nonce
position; session-key registration deliberately uses a *fresh* nonce anchor instead — these are
different conventions for different operations, both handled internally by `lib/exchange.ts` /
`lib/agent.ts`. See `docs/tasks.md` tasks 5–6 for the full derivation.

## Money-safety in trading

Enforced in `lib/execute.ts` (`executeBuy`/`executeShort`/`executeSell`, see
[tasks.md task 6](./tasks.md) for the full derivation): a plan that's invalid or fills nothing
throws before anything executes (safe to retry); once any leg fills, the code never throws again
— it reports `partial`/`persisted` flags instead, so a real fill is never mistaken for "nothing
happened." Balances are re-read immediately before execution (`BuyForm`/`ShortForm` refetch right
before calling `executeBuy`/`executeShort`).

## Known limitations

| Limitation | Impact | Planned fix |
|------------|--------|-------------|
| Cross-tab lot writes not atomic | Two tabs trading the same wallet at the same instant can lose one update's **local** bookkeeping (on-exchange fills stay correct). | `navigator.locks` + re-read/merge (carried over unfixed from the reference project). |
| Corrupt storage reads as empty | `loadLots`/`loadTokensets` return `[]` on a parse error, looking like "no positions"/"no tokensets". | Distinguish and warn. |
| No fee headroom in the funds guard | A near-exact-balance buy could be rejected by the exchange once fees are taken into account. | Add a fee buffer (carried over unfixed from the reference project). |
| `risex-client`/signing logic provenance | The exact EIP-712 struct layouts, nonce conventions, and order-encoding bit-packing were derived by reading the `risex-client` community SDK's source (`github.com/SmoothBot/risex-ts`), which describes itself as "unofficial, not production ready." **Two confirmed bugs found in it via real mainnet testing** (both fixed here, both specific to the leverage-update action — order placement itself has been separately confirmed correct on each point checked so far, but still hasn't been exercised with a real signed order): (1) the request field name is `permit` in the SDK for every write endpoint, but the live API rejects that for `/v1/account/leverage` specifically with `"permit_params is required"` (`/v1/orders/place` genuinely does use `permit` — the field name is inconsistent across RiseX's own endpoints). (2) The SDK's `encodeLeverage` hash formula (`uint256(marketId) + uint128(leverage)`, no action-type-hash prefix) is simply wrong — it produced a signature that recovered to a different address than the actual signer ("permit signature mismatch"), confirmed by rebuilding the hash per developer.rise.trade's documented formula (`keccak256(abi.encode(keccak256("RISE_PERPS_UPDATE_LEVERAGE_V1"), uint16(marketId), uint8(leverage)))`) instead. **Given two independent bugs found in the SAME code path (leverage), treat every other action this SDK's pattern was used for (order placement, and margin-mode/isolated-margin if ever implemented) as unverified until each is independently exercised against the live API or its exact formula is confirmed from developer.rise.trade's reference, not assumed from the SDK.** | Run a real `register-signer` call and a real order on testnet/mainnet before fully trusting order placement; verify `encodeOrder`'s hash formula against developer.rise.trade the same way `encodeLeverage`'s was, rather than resting on the earlier `ethers` cross-check (which only proved the port matched the SDK, not that the SDK was right). |
| Fill price lookup can fail | `placeOrder`'s own response has no fill-price field; the app fetches it via a follow-up `GET /v1/orders/by-id/{id}` call. If that call fails after a real fill, the app falls back to the submitted limit price (a safe, conservative estimate) and flags the leg `priceUnconfirmed` rather than losing track of the fill — but the displayed cost basis is an approximation until that's reconciled. | Reconcile from `trade-history` once available, or retry the lookup. |
| Mainnet deposit path unresearched | The confirmed `deposit-usdc` endpoint is a testnet-only faucet; real USDC funding on mainnet uses a separate flow not yet investigated. | Research before trading with real funds. |
| Undocumented per-action rate limits | `/v1/account/leverage` rate-limits to **1 request/second** — not mentioned anywhere in the public docs, found live ("rate limited: 1 request per second for update_leverage") when a 2+ market tokenset set leverage back-to-back. `execute.ts` now throttles sequential leverage calls with a 1100ms gap (a guessed-safe margin, not a confirmed exact window). Other write actions (`/v1/orders/place` in particular) may have their own undocumented per-action limits that haven't been hit yet. | Tighten the margin only once independently confirmed; watch for a similar rate-limit error on order placement for larger tokensets. |
